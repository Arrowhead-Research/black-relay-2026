# Runbook: the central broker

Operating the central MQTT broker (see [README.md](README.md) for why it exists). On the central
server (172.22.41.10) it is the `broker` service of the repo-root `compose.yaml`, checked out at
`/srv/sensor-fusion`. Run everything below from there unless a step says otherwise.

## What runs

| | |
|---|---|
| Service | `broker` (Mosquitto 2.1.2), part of the `black-relay-central` project |
| Ports | 1883 (login) and 8883 (TLS + login), on `BIND_ADDRESS` only; see [PORTS.md](PORTS.md) |
| Config | `detection/central-broker/mosquitto.conf`, `aclfile`, `entrypoint.sh`, mounted read-only |
| Logins | repo-root `.env`, written by `detection/central/make-env.sh` (run by `setup-central.sh`). Never commit it |
| TLS certificate | `detection/central-store/state/tls`, the Let's Encrypt certificate when `--domain` was used |
| Data | the `broker-data` volume (persistent sessions, so fusion misses nothing while it is down) |

`entrypoint.sh` rebuilds the password and ACL files from the environment at every start. To add a
login or change a password, change `.env` and recreate the broker: `docker compose up -d broker`.

## Logins and what each may do

Mosquitto denies anything the ACL does not list. A publisher cannot read, and cannot write outside
its prefix.

| Login | Env keys in `.env` | Allowed |
|---|---|---|
| `fusion` | `BROKER_FUSION_USER` / `_PASSWORD` | read `detection/#` |
| `physical-subsystem` | `BROKER_PHYSICAL_*` | write `detection/physical/#` |
| `rf-console` | `BROKER_RF_*` | write `detection/rf/#`, read `detection/rf/sim/#` |
| `rf-analytics` | password generated by `rf-bootstrap` into the `rf-secrets` volume | write `detection/rf/#` |
| `relay` | `BROKER_CAMERA_*` | the shared camera kit login: write `detection/camera/#`, read `detection/rf/cues/camera` |
| `relay-api` | `BROKER_RELAY_API_*` | read the three `detection/camera/` topics the relay API stores |
| `rf-node-<node>` | `BROKER_RF_NODE_LOGINS` | write `detection/rf/nodes/<node>/#` |
| `cam-node-<node>` | `BROKER_CAMERA_NODE_LOGINS` | write `detection/camera/#`, read `detection/rf/cues/camera` |

`make-env.sh` makes the per-node logins for every node in the fleet inventory
(`detection/rf-subsystem/node/fleet/ansible/inventory.yml`), so they exist before a node is
provisioned. To add one by hand, on the server:

```sh
detection/central/node-logins.sh rf wbt-5          # or: camera cam-5
```

It keeps existing logins and recreates the broker. `detection/central/node-secrets.sh` prints
the same logins for provisioning the nodes (see `DEPLOY.md`).

## Check it

```sh
docker compose ps broker                      # healthy
docker compose logs broker | tail
```

The healthcheck subscribes as `fusion`, so "healthy" proves the listener, the password file and the
ACL. To watch traffic:

```sh
docker compose exec broker sh -c 'mosquitto_sub -h 127.0.0.1 -u "$BROKER_FUSION_USER" -P "$BROKER_FUSION_PASSWORD" -t "detection/#" -v'
```

In a second shell, publish as the physical login. The first message must appear in the subscriber;
the second must not (the ACL drops it and the publisher is not told):

```sh
docker compose exec broker sh -c 'mosquitto_pub -h 127.0.0.1 -u "$BROKER_PHYSICAL_USER" -P "$BROKER_PHYSICAL_PASSWORD" -t detection/physical/test -m allowed'
docker compose exec broker sh -c 'mosquitto_pub -h 127.0.0.1 -u "$BROKER_PHYSICAL_USER" -P "$BROKER_PHYSICAL_PASSWORD" -t detection/rf/test -m denied'
```

Anonymous must be refused ("Connection Refused: not authorised"):

```sh
docker compose exec broker mosquitto_pub -h 127.0.0.1 -t detection/physical/test -m anon
```

TLS, from another machine (expect the domain's certificate, a Let's Encrypt issuer):

```sh
openssl s_client -connect 172.22.41.10:8883 -servername reg.bulexa.com </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -enddate
```

From a publisher's host, `nc -zv 172.22.41.10 8883` shows the port is reachable.

## Fusion's view

Fusion has one broker entry, `central` (`detection/central/fusion.config.yaml`, site `sh1`), logging
in as `fusion`. Check it with the API:

```sh
set -a; . ./.env; set +a
curl -s -H "Authorization: Bearer $FUSION_API_TOKEN" http://172.22.41.10:8090/api/v1/health | python3 -c 'import json,sys; h=json.load(sys.stdin); print([(b["id"], b["connected"], b["counts"]) for b in h["brokers"]])'
```

`connected` should be true and `accepted` should rise while nodes publish. `/api/v1/nodes` lists the
RF nodes, camera kits and `physical-bridge-01`.

## Physical bridge

The bridge publishes as `physical-subsystem` with the password in
`deploy/secrets/fusion/fusion_password` (owner uid 10003, mode 0400), as the `fusion` profile's
`fusion` container. `setup-central.sh --with-bridge` sets this up for a bridge on the same server;
for a bridge on another host, hand it its login with `detection/central/share-broker-login.sh <name>`
and fetch it there with `deploy/scripts/fetch-broker-login.sh`. In `deploy/config/config.yaml`
the `fusion` block needs `host`, `port` (8883 with `tls: {ca_file: ...}`, or 1883 with `tls: null`),
`username: physical-subsystem` and `password_file: /run/secrets/fusion_password`.

Check it from the bridge's folder:

```sh
docker compose --profile fusion logs fusion | grep -E 'fusion publisher up|connected|refused'
```

Expect `fusion publisher up: <host>:<port> prefix=detection/physical site=sh1`, then `connected`.
A wrong password shows as a connect failure with reason code 5.

Outage test, worth doing once: `docker compose stop broker` on the central server, trip a sensor,
`docker compose start broker`. The bridge's outbox replays the event with its original `id` and
`timestamp`, and fusion stores it once.

## RF and camera publishers

- The RF console and rf-analytics start with the central project and log in as above; the console
  logs `publishing positions and node status to ...`. Within 60 seconds the subscriber shows
  `detection/rf/status/nodes`, and `detection/rf/positions` once a device has readings.
- WBT nodes and camera kits log in with their own `rf-node-<node>` and `cam-node-<node>` logins,
  installed by the fleet playbook (`detection/rf-subsystem/node/fleet`). `detection/rf/nodes/<node>/health`
  and `detection/camera/status/nodes` show them.
- The camera relay API reads the camera topics as `relay-api`; its bundled broker (the `broker`
  profile of `camera-relay-service`) stays off.

## Running the broker alone

`compose.yaml` in this directory starts only the broker, for a test machine:

```sh
cd detection/central-broker
BROKER_BIND_ADDRESS=<address> ./setup-credentials.sh     # writes .env, refuses to overwrite one
docker compose up -d
```

It publishes 1883 only. The simulator (`detection/simulator-deploy`) mounts the same configuration
files for its own broker.

## Troubleshooting

| Symptom | Cause |
|---|---|
| `broker` restarting, log says a broker user cannot hold a colon, ampersand, pipe, backslash or space | a login name in `.env` has one of those characters |
| `BROKER_RF_ANALYTICS_USER is set without ...` | `rf-bootstrap` has not written `analytics-broker-password` yet; `docker compose up -d` again |
| Publisher connects but its messages never arrive | it published outside its prefix; the ACL drops it silently |
| Connect failure, reason code 5 | wrong login or password; recreate the broker after changing `.env` |
| 8883 shows the wrong certificate | the broker has not restarted since the certificate was renewed or replaced: `docker compose restart broker` |
